## Verdicts

1. **`locators` vs `locators[]`** — `locators[]` is **correct**; plain `locators` is **wrong**. The hypothesis in `tools/projects.py`'s docstring is backwards. A single plain `locators=&lt;one&gt;` returns `400 "expected array, received string at \"locators\" or ... expected \"all\""`; `locators[]=&lt;one&gt;` returns `200 {"created":1,"errors":{}}` and the assignment verifiably takes effect. Plain *repeated* (`locators=a&amp;locators=b`) works — classic `qs` single-vs-array parsing — so the bug only bites one-project calls. Same result for `PUT /v2/projects/labels` and `GET /v2/projects`; `DELETE /v2/projects` tolerates both. `POST /v2/projects`'s JSON body correctly uses plain `locators`.
2. **Package labels** — "blank for all versions" means **omit the key** (stores `null`); `""` is stored literally and matches nothing, `null` is a `400`. `scopeId` must be **absent** for `org` scope (sending it → `500`) and **present** for `project`/`revision` (omitting → `500`). `POST /organizations/labels` with `{}` → `400 "Create label missing required param: 'label'"` — the spec's empty `required` list is a defect.
3. **`GET /counts/builds`** — both defects confirmed: returns a **bare JSON number** (1-byte body), and `locator`/`projectId` is required with exactly the 400 text the spec's own example shows.
4. **Org settings propagate** — `DESTRUCTIVE` is right. A per-project override was set, propagated, and **destroyed**, while a second override not named in the key list survived. Propagation is scoped to the named keys and does not alter the org defaults themselves.
5. **`POST /oidc/token-exchange`** — a *valid* `Authorization` header is ignored (byte-identical `400`s with and without it), but an *invalid* one returns `401` before the endpoint's own validation. So the header is not inert: a caller with no FOSSA token — the actual use case — cannot send a placeholder. The success path is unreachable without an OIDC trust relationship; that remains unresolved.
6. **`github-app/installation-url`** — `302`, empty body, `Location: https://github.com/apps/fossa-integration/installations/new`, byte-identical across calls, no `state`/nonce. Stable and public: a tool should not follow the redirect, just return the header.

## 1. HIGH — `fossa_get_project_associations` (`905c9a2`)

Sections are now independent. Each is attempted; an answered-but-rejected request is recorded in a new per-section `errors` map (`status_code`, `error_name`, `message`) while the sections that answered still land in `data`. The two keys are disjoint, so an *empty* section (present in `data` as `[]`/`{}`) stays distinguishable from a *failed* one (absent from `data`, present in `errors`). Only `FossaApiError` is caught — a transport or config failure isn't a fact about one section and still aborts the aggregate.

`last_published` left the default set (defaults are now `labels` + `release_groups`) but remains a valid `sections` value, so the capability is intact. The docstring says FOSSA's 404 reports the date as *not known* rather than the project or endpoint as missing, and stops there — it doesn't assert a cause the audit didn't establish.

Verified by four tests: all-three-sections explicit, default omits `last-published` (asserts that route uncalled), one 404 alongside a successful and an empty section, and every-section-fails.

## 2. MEDIUM — `fossa_update_org_settings` (`30d4950`)

`action="replace"` now requires `DESTRUCTIVE`. Since `action` is a closed `Literal` of `replace`/`propagate`, the tool has no plain-WRITE path left — correct for a statically `destructiveHint=True` tool. `propagate` stays `DESTRUCTIVE`, ADMIN sections still require `ADMIN`, two-tier calls still check twice. `_required_tiers` lost its now-non-discriminating `action` parameter.

**Wording did need updating, and the repo disagreed with itself.** `server.py` already described the destructive tier as covering "the writes that replace state wholesale rather than merging into it" — so its invariant comment needed *no* change and is now actually true. But `writes.py` and `DECISIONS.md` both defined the tier as deletes + unbounded bulk targets *only*, which wouldn't have justified this fix. I widened both to include wholesale replacement, added the specific rationale to `DECISIONS.md`'s "tier follows blast radius" bullet, and fixed `_TIER_RATIONALE[DESTRUCTIVE]` so an operator refused on a replace is told the real reason rather than "deletes FOSSA state".

Three new refusals pin it: replace under writes-only, replace of an ADMIN section under writes+admin (proving ADMIN alone doesn't unlock the PUT), and that no section computes a plain-WRITE tier. That last one asserts on `_required_tiers` directly — routing it through the tool would hit `ValidationError` from body validation first and prove nothing about the gate.

## 3. LOW — `fossa_get_builds` (`eaac9e0`)

`BuildReadInput` now requires **exactly one** of `locator`/`project_id`, refusing before any request is built. Exactly one rather than at least one: they ask different questions (one revision vs. every revision of a project) and the spec doesn't say which wins when both are sent. Recorded as a spec defect in both model and tool docstring — same verdict as the `locators[]` case. Two new tests assert zero HTTP calls (no target, both views; and both targets); the existing list-query test dropped `project_id` and a new sibling covers that parameter alone.
