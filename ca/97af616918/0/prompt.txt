## The bulk endpoint — the one you flagged

`POST /package-label-assignments/bulk` is **WRITE**, not DESTRUCTIVE. It has no filter mode at all: the target set is `packageLocators`, an explicit `minItems: 1` list, and the operation only adds — the spec says duplicate assignments are skipped, nothing is removed. It is a server-side loop over the single-package assign.

The endpoint that actually earns DESTRUCTIVE here is `PUT /package-label-assignments`. It is a reconcile: *"Existing assignments not present in the map are removed."* The target set is implicit (everything for that package at that scope) and removal is silent, so it is DESTRUCTIVE despite being a `PUT` — DECISIONS.md §7, tier follows blast radius.

## Blank `packageVersion` — decision

**Not expressible anywhere in the module.** FOSSA reads a missing `packageVersion` as *all versions*, so an omission is a widening, not a narrowing.

- `assign_package_labels` requires **exactly one** of `package_version` (non-blank, `min_length=1`) or `apply_to_all_versions: bool = False`. Neither → `ValueError`; both → `ValueError`. All-versions is only reachable by naming a flag that says so, and the body then **omits** the `packageVersion` key rather than sending `""`.
- `bulk_assign_package_label` exposes `apply_to_all_versions` mapping to the endpoint's inverted `shouldUseSpecificVersion`, always sent explicitly so the version behavior is visible in the wire body rather than inherited from FOSSA's default. Locators must contain `$`, so a caller cannot reach all-versions by dropping the version off a locator either.
- The read tool's `package_version` filter is `min_length=1`; FOSSA's empty-string "all-versions rows" filter is not exposed, since `include_package_wide_labels` reaches the same rows alongside a real version.
- The one place "every version" is data is `set_package_label_assignments`'s `new_label_ids`, where `"all"` is the key the endpoint itself defines. That is a key the caller typed, not an omission.

## Credentials — read this part

**No read in this domain can return a credential**, and that is a property of the API, not of my code. FOSSA's OIDC federation is keyless: a provider is `{issuer, scope}`, a trust relationship is `{audiences, requiredClaims}`. There is no client secret field anywhere. `available-service-accounts` returns ids/usernames/emails — identity, not secrets. The SAML `cert` is the IdP's X.509 *public* signing certificate (published in IdP metadata by design); no private key or SP signing key exists in this surface. And there is no `GET /organizations/{id}/saml` at all, so no SAML read tool exists.

**One operation does return a live credential: `POST /oidc/token-exchange`.** Its 200 body contains `credential.token` — a working FOSSA API token. It is a write, not a read, but it is the real exposure here.

What I did: `fossa_exchange_oidc_token` **does not return the token.** It returns the resolved identity (`userId`, `providerId`, `issuer`, `subject`) and credential metadata (`isPushOnly`, `expiration`) with the token replaced by a placeholder and a `token_minted: true` flag. The redaction is an **allow-list**, not a deny-list: only the four documented top-level fields are copied by value, and anything else in the response is reported by *name* under `undocumented_fields`, so a field added to that endpoint later cannot carry a secret into a tool result before a human has looked at it. There is no argument that turns redaction off. Tested by `test_exchange_oidc_token_never_returns_the_minted_token`, the same standard as `test_token_absent_from_tool_output_and_logs`.

The tool is therefore a "does my trust relationship actually work?" verifier, not a way to get a token; the docstring says so, and says the token is still minted and still valid until expiry even though nobody can read it. **This is the judgment call in this branch most worth a second opinion** — the alternative was not exposing the operation at all, which would break the "every operation reachable" rule.

Two other notes on that endpoint: the spec declares it as the API's only **unauthenticated** operation (`security: null`), but `FossaClient` attaches `Authorization` to every request and I did not add a bypass; I could not verify live whether FOSSA minds the extra header. And it is a `POST`, so it is never retried — correct, since a replay would mint a second token.

## Safety behavior added beyond the API

`requiredClaims` with a `sub` value that is nothing but wildcards (`*`, `**`) is refused before any request is built. FOSSA accepts it; it would let every token that issuer ever signs authenticate as the named service account. That is the OIDC equivalent of `locators=all` on the bulk project delete, and it is refused for the same reason. Narrowing patterns like `repo:acme/*` are allowed. Also enforced: the `oneOf` scope/`scopeId` pairing on both create endpoints (a flat signature can't express it), and `organization_id` for SAML falls back to `FOSSA_ORG_ID` but refuses to guess when neither is set.

## Notes and things worth flagging

- **`client.request_json` on 204.** Five operations here answer 204 (Jira PATCH, both snippet reject endpoints, both deletes) and two of those carry a JSON body, so `request_text` (the `projects.py` idiom) doesn't apply. I duplicated `_request_tolerating_empty_body` from `tools/issues.py` rather than touch `client.py`; the docstring says so and says the real fix belongs in the transport layer. That helper now exists twice — worth consolidating in a pass that owns `client.py`.
- **Snippet query arrays use plain repeated keys**, not `key[]=`. The vendored spec puts brackets in the parameter *name* wherever FOSSA wants them (`locators[]`, `depth[]`); none of `ids`, `packageIds`, `rejectionStatus`, `packageLabels`, `vendoredMatch` have them.
- **`fossa_set_custom_risk_score` requires an explicit `action`.** FOSSA publishes no read endpoint for a custom risk score, so the tool cannot discover whether one exists and POST-vs-PATCH cannot be inferred. Guessing would turn a wrong guess into a 4xx; the parameter is a `Literal["create","update"]`.
- **Report options: 26 booleans, expressed as two on-lists.** `sections` and `dependency_data` name what should be ON; the tool sends every switch in a supplied group explicitly. An omitted group is not sent, which is what makes `PUT`'s deep merge usable. Create rejects a missing group locally rather than letting FOSSA 400.
- **`GET /revisions/{locator}/snippets/{snippetId}/matches/{path}` has an untyped `matchDetails`** in the spec (no declared schema) and returns matched source lines. It's the only unbounded payload here; it's capped at `FOSSA_REPORT_MAX_CHARS` and returned as truncated JSON text with `truncated` / `original_char_count` when the cap bites.
- **Nothing in these domains was left unmodeled.** All 28 operations are reachable. One adjacent gap belongs to Issues, not here: the Issues commit notes it did not expose the `PUT /v2/issues` `export` body variant because it needs the Jira configuration surface — that variant is still unexposed, and now that `GET /jira` exists someone could revisit it.</result>
