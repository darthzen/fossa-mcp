## COVERAGE

18 operations sit under `/projects*` + `/v2/projects*`. 15 are covered by these tools; 2 belong to other domains (`GET /projects/{locator}/revisions` → `revisions.list_project_revisions`; `PUT /v2/projects/policy` → `policies.assign_security_policy_to_projects`); 1 is deliberately not exposed:

- **`GET /projects/{locator}/export-issues`** — the umbrella path is the same operation as the two format-specific paths, selected by a `format` query parameter instead of the path segment. The tool calls `/export-issues/json` or `/export-issues/csv`, which is unambiguous about the response media type. Nothing is unreachable as a result.

`PUT /projects/{locator}` exposes 23 of the endpoint's 53 body fields: `title`, `description`, `project_url`→`url`, `notes`, `public`, `default_branch`, `tracking_branches`, `hidden_branches`, `policy_id`, `security_policy_id`, `quality_policy_id`, `sbom_policy_id`, `policies_approve_multilicense`, the four `*IssueScanningEnabled`/`sbomAnalysisEnabled` flags, the three `*StatusCheckEnabled` flags, `label_ids`→`labels`, `transitive_excludes`, `report_custom_text`. Left out: the nested config blocks (`issueTrackerCustomFields`, `notifications`, `filters`, `bom_column_settings`, the other `issueTracker*` arrays, `issue_tracker_url`/`type`, `useGlobalTrackerSettings`), the snippet/vendored/quick-import scanning flags, the container `excludeBaseLayerIssues*` trio, `integrationhook_*`, `scm_url`/`manual_scm_url`/`vcs_host`, `defaultSavedOption*`, `snippetAutoRejectMatchPercentageThreshold`, and the FOSSA-populated `invalidCredential`/`bom_public_id`. Every field defaults to `None` and `to_payload()` dumps with `exclude_none=True`, so an unnamed field never appears in the body — which also means clearing a nullable field to `null` is not expressible through this tool.

## NOTES

1. **`locators` vs `locators[]`.** `policies.py` sends `locators[]` to `PUT /v2/projects/policy`; the spec declares the parameter as `locators` on that endpoint and on both `DELETE /v2/projects` and `PUT /v2/projects/labels`. I used the spec-declared `locators`, repeated. Rationale, also stated in the module docstring: on a bulk delete, a parameter name FOSSA does not recognize degrades the request into "every project matching the filters", and with no filters that is the whole organization. Repeated `locators` parses as an array under `qs` and degrades to a single locator under a naive parser. Worth verifying both spellings against a live org and reconciling `policies.py` — I did not touch it.
2. **`fossa_delete_projects` sends no filter parameters at all**, only locators, so there is nothing for FOSSA to widen the target set with. `"all"` is rejected in the input model for both this tool and `fossa_apply_project_label`.
3. **`list_projects` now issues a POST** when the encoded query exceeds 1800 characters (a long `locators` filter), per the endpoint's documented purpose. It remains read-only and keeps `readOnlyHint=True`; existing `test_tools.py` assertions are unaffected. `POST` is never retried by `client.py`, which is correct here since it is a read.
4. **Empty-body responses.** `DELETE /projects/{locator}` returns 200 with no body and the slug delete returns 204; `request_json` would raise `FossaApiError("Invalid JSON response")` on both, so the three delete tools use `request_text`. `PUT .../generate_attribution_slug` returns a bare JSON string, and `GET .../last-published` returns a bare ISO timestamp string — both pass through `request_json`, whose declared return type (`dict | list`) is narrower than what FOSSA actually sends. No change to `client.py` was needed.
5. **`server.py` instructions string is now stale** — it says "Every tool is read-only except the two security policy tools." That needs rewriting once the parity tools are registered.
6. **`GET /projects/{locator}/labels`** is tagged `Project Labels` in the spec rather than `Projects`; I covered it here because it is addressed by project locator, but flag it in case the Labels domain agent also claims it.</result>
